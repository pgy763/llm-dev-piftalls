# 事务里调模型，把连接池拖垮了

![报错原文](/images/java-cannotgetjdbcconnectionexception.png)

> 上图按本条「报错」原文渲染，文本逐字一致 —— 可以直接拿去和你的日志比对。

## 报错

```
org.springframework.jdbc.CannotGetJdbcConnectionException: Failed to obtain JDBC Connection
	...
Caused by: java.sql.SQLTransientConnectionException: HikariPool-1 - Connection is not available,
request timed out after 30000ms.
```

## 现象

平时没事，**一到大模型变慢或并发上来**，整个服务的数据库访问开始超时。报错指向数据库，但数据库本身很健康。

## 为什么

看这段代码，几乎每个人都写过：

```java
@Transactional
public void handle(String question) {
    Doc doc = docRepo.findById(id);            // 占用连接
    String answer = llm.chat(question);        // ← 3~30 秒，连接一直不还
    recordRepo.save(new Record(doc, answer));  // 还是同一条连接
}
```

`@Transactional` 的语义是「整个方法一个事务」，事务持有连接直到方法返回。而模型调用要几秒到几十秒 —— **高峰期等于把连接池按并发数除以 10（默认池大小）直接耗尽**。

关键认知：**连接池的瓶颈不是 QPS，是「连接被持有的时长」**。

```
可用并发 = 池大小 / 单请求持有连接的时间
10 个连接 / 每次 10 秒 = 1 并发
```

## 怎么改

### 一、把外部调用移出事务

```java
public void handle(String question) {
    Doc doc = tx.read(id);              // 短事务，查完就提交
    String answer = llm.chat(question); // 事务外
    tx.write(record);                   // 另一个短事务
}
```

### 二、注意 `@Transactional` 自调用不生效

```java
// 错：在同一个类里调自己，事务注解不生效（没走代理）
public void handle() {
    this.saveRecord();   // 没有事务
}

@Transactional
public void saveRecord() { ... }
```

要拆成两个 Bean，或者注入自己（`@Lazy`），或者用 `TransactionTemplate` 显式控制边界。

### 三、必须在一个事务里时，用编程式事务把范围缩到最小

```java
return transactionTemplate.execute(status -> {
    Record r = recordRepo.save(...);
    return r;                      // 只包含写库，模型调用放外面
});
```

## 怎么预防

- **Code Review 硬规则：事务方法里禁止出现外部 IO**（HTTP、模型、文件、消息队列）
- 加一个监控：事务平均耗时。超过 1 秒的事务要能列出调用点
- Hikari 的 `connectionTimeout` 调短（比如 5 秒），让问题更快暴露，而不是挂着 30 秒拖死线程

## 环境

| 组件 | 版本 |
| --- | --- |
| JDK | 17 / 21 |
| Spring Boot | 3.x |
| 连接池 | HikariCP 默认 10 个连接 |
| 触发条件 | `@Transactional` 方法里调用模型接口 |
| 相关异常 | `CannotGetJdbcConnectionException`、`SQLTransientConnectionException` |
